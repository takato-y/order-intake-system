## 1. ジョブ一覧

| ジョブ名 | 機能 | 起動 | 実行内容 | 所要時間の目安 | 失敗時 |
|---|---|---|---|---|---|
| 受注メール取込 | FN-001 | メール受信ごと（Webhook） | 抽出・検証・登録 | 規則抽出は 1 秒未満、LLM はモデルと PC 性能に依存（本検証の環境では 1 通数秒） | 応答コードと n8n の実行履歴を確認 |
| 月次集計 | FN-008 | 毎月 1 日 6:00（タスクスケジューラ） | 前月分の CSV・xlsx を出力 | 数秒 | 終了コード 0 以外。ログを確認して再実行 |
| 月次帳票作成 | FN-009 | 毎月 1 日の業務開始後（担当者が手動） | CSV から帳票を作成 | 数秒 | メッセージの内容に従う |
| DB バックアップ | — | 毎日 22:00 | DB ファイルの複製 | 数秒 | 次回実行で再取得 |

### 1.1 月次集計の登録例

Windows（タスクスケジューラ）：

```
schtasks /Create /TN "OrderIntake\MonthlyReport" /SC MONTHLY /D 1 /ST 06:00 ^
  /TR "powershell -NoProfile -ExecutionPolicy RemoteSigned -File C:\apps\order-intake-system\batch\run_monthly.ps1"
```

実行ポリシーは RemoteSigned とする（署名のないスクリプトを無条件に許可する Bypass は使わない）。インターネットから取得した zip を展開した場合は、`Unblock-File batch\run_monthly.ps1` でブロックを解除してから登録する。

Linux（cron、同じ PC で API が動いている場合）：

```
0 6 1 * * cd /opt/order-intake-system && .venv/bin/python -m batch.monthly_report >> output/monthly.log 2>&1
```

## 2. 日々の確認

| 確認内容 | 方法 | 頻度 |
|---|---|---|
| 取込エラーの有無 | 取込エラー一覧（`GET /rejections`。例：`curl -s "http://localhost:8000/rejections?limit=50"`）で前日以降の記録を確認し、元のメールを見て手で登録する | 毎朝 |
| API の稼働 | `GET /health`（Docker では healthcheck） | 常時 |
| n8n の失敗実行 | n8n の実行履歴で Error を絞り込む | 毎朝 |

## 3. 障害対応表

詳しい対応は 09_障害対応手順書.md を参照する。

| 事象 | 想定原因 | 確認 | 対応 | 再実行 |
|---|---|---|---|---|
| Webhook が 503（ERR-007） | API の停止・接続先の誤り | `GET /health`、n8n「設定」の api_url | API を起動・接続先を修正 | 同じメールを再送してよい（重複しない） |
| 取込エラーが急に増えた | 取引先のメール書式の変更、LLM の停止 | 取込エラーの理由、API ログの LLM 切替 | 規則の項目名を追加、LLM を再起動 | 元のメールを再送 |
| すべて extractor=rule になる | LLM の停止・モデル未取得 | API ログの「LLM fallback」、Ollama の `/api/tags` | LLM を起動・モデルを取得 | 不要（登録済み） |
| 月次集計が終了コード 1 | API の停止・DB ファイルがない | バッチのログ | API を起動、または `--db` で DB を直接指定 | `run_monthly.ps1 -Month YYYY-MM` |
| 帳票マクロが「見出しが想定と異なります」 | 別のファイル・古い形式の CSV を選んだ | ファイル名と 1 行目 | 正しい CSV を選ぶ | マクロを再実行（同じ月は置き換え） |
| 集計の数字が合わない | 顧客名・商品名の表記揺れ | `GET /orders?month=` で明細を確認 | マスタの名寄せ（対象外の運用作業） | 名寄せ後に月次集計を再実行 |

## 4. バックアップと戻し方

| 対象 | 方法 | 保管 | 戻し方 |
|---|---|---|---|
| DB（SQLite） | 毎日 `sqlite3 data/orders.db ".backup backup/orders_YYYYMMDD.db"`（書き込み中でも整合した複製が取れる） | 30 日分 | API を停止し、複製を `data/orders.db` に置き換えて起動 |
| DB（SQL Server 移行後） | 完全バックアップ（日次）＋ログバックアップ | 運用規程に従う | 時点復旧 |
| n8n フロー | `n8n/order-intake.json` をリポジトリで管理 | Git | n8n に取り込み直す |
| 月次 CSV・xlsx・帳票 | 共有フォルダに月ごとに保存 | 7 年（帳簿書類の保存に合わせる想定。期間は社内規程で確認） | — |

Docker で動かしている場合、DB はボリューム `order-data` の中にある。`docker compose cp api:/data/orders.db ./backup/` で取り出せる。

## 5. 設定値の管理

| 設定 | 置き場所 | 備考 |
|---|---|---|
| DB_PATH、EXTRACTOR_MODE、OLLAMA_URL、OLLAMA_MODEL、LOG_LEVEL | 環境変数（docker-compose.yml） | 秘匿値ではない |
| n8n の実行履歴 | フローの設定（成功時は保存しない、失敗時は保存） | 失敗時の履歴にはメール本文が残る。n8n の実行データの自動削除を有効にし、保存期間を短くする |
| n8n の接続先 | n8n「設定」ノード | 外部の LLM サービスを使う場合、API キーは n8n の資格情報に登録し、フローの JSON には書かない |

## 6. 定期点検

2 章の日々の確認に加え、次を点検する。

| 時期 | 点検すること | 方法 |
|---|---|---|
| 毎日 | 2 章の確認（取込エラー・API の稼働・n8n の失敗実行） | 2 章のとおり |
| 毎日 | DB バックアップが取れているか | `backup/` に当日の `orders_YYYYMMDD.db` があるか |
| 毎月（月初） | 月次集計が正常に終わったか | タスクスケジューラの前回の実行結果が 0（正常終了）、`output/logs/` のログ（cron の例では `output/monthly.log`）に `出力しました` があるか |
| 毎月（月初） | 取込エラーのうち、手で登録していないものが残っていないか | `GET /rejections` の各記録の Message-ID が `GET /orders?month=YYYY-MM` の一覧にあるか（ないものは手で登録する） |
| 毎月 | ディスクの空き、古い DB 複製・ログの整理 | `df -h`。保管期間（4 章）を過ぎた複製を整理する |
| 毎月 | 戻し方の確認 | DB の複製を別の場所に戻し、`sqlite3 <複製> "PRAGMA integrity_check;"` が `ok` を返すか |
| 変更時 | n8n フロー・API・Ollama のモデルを変えたとき | `python -m pytest -v` が合格すること。n8n フローは 07_テスト仕様書.md の TC-030（サンプル 7 通の送信）で確認する |
| 変更時 | n8n の版を上げたとき | 「設定」ノードの値と、実行履歴の設定（成功時は保存しない）が保たれているか。Gmail Trigger を使う場合は出力項目名（05_インターフェース設計.md 3.2） |

点検の結果を残す場所と様式は運用で決める項目とする。

## 7. 資格情報・鍵・トークンの更新

本システムの既定の構成には、更新が必要な資格情報はない（該当なし）。受注 API と n8n の Webhook は社内ネットワーク専用で認証を設けておらず、Ollama もローカルで動かすため API キーを使わない。5 章の環境変数はいずれも秘匿値ではない。

次の場合に限り、資格情報の更新が必要になる。

| 対象 | 保管場所 | 更新の手順 |
|---|---|---|
| 外部の LLM サービスの API キー（Ollama 以外を使う場合） | n8n の資格情報（フローの JSON・リポジトリには書かない） | 新しいキーを発行する → n8n の資格情報の値を差し替える → サンプルのメール 1 通で抽出できることを確認する → 古いキーを失効させる |
| Gmail Trigger の接続（Gmail から直接取り込む場合） | n8n の資格情報 | 接続が切れたら n8n の資格情報から接続し直し、テスト用のメールで取り込めることを確認する |
| API・Webhook の認証（外部に公開する場合。02_方式設計.md の 6 章） | 公開時に決める | 公開時に本章へ追記する |

更新の周期は運用で決める項目とする。

## 8. 連絡体制

| 役割 | 担当すること | 連絡先 |
|---|---|---|
| 利用者 | 受注メールの扱い・帳票について異常に気づいたら運用担当者に連絡する。月次帳票マクロのメッセージを伝える | 運用担当者 |
| 運用担当者 | 日々の確認・定期点検、09_障害対応手順書.md による一次対応（再送・手での登録・再起動・DB の戻し）、障害の記録 | 保守担当者 |
| 保守担当者 | コード・フロー・設定の修正を伴う二次対応、原因の調査、再発防止 | — |

連絡は利用者 → 運用担当者 → 保守担当者の順に行う。担当者の氏名・連絡先・連絡手段・対応時間は運用で決める項目とし、本書には書かない。
