## 1. 業務の背景と目的

想定する業務は、事務用品を扱う架空の卸売会社（以下「当社」）の受注事務です。取引先からの注文は大半がメールで届き、担当者が本文を読んで受注台帳（Excel）に手で転記しています。月末には台帳を顧客別・商品別に集計し、月次の受注帳票を作成しています。

本システムの目的は、次の 3 点です。

- メール本文からの転記作業をなくし、入力ミスと転記漏れを減らす
- 同じメールの二重転記を仕組みで防ぐ
- 月次帳票の作成を、集計から体裁の整った帳票の出力まで定型化する

## 2. 現状の課題

| No | 課題 | 影響 |
|---|---|---|
| 1 | 本文の読み取りと転記を手で行っている | 1件あたり数分の作業。数量・納期の転記ミスが発生する |
| 2 | 再送メール・転送メールを別の注文として登録してしまう | 二重出荷・在庫の引当誤り |
| 3 | 注文の書き方が取引先ごとに異なる | 決まった項目名で書かれていない注文の読み落とし |
| 4 | 月次集計を手作業の関数とピボットで行っている | 担当者に依存し、毎月まとまった作業時間がかかる |

## 3. 機能要件

| ID | 要件 | 優先度 |
|---|---|---|
| REQ-001 | 受注メールを受け取り、本文から顧客名・商品・数量・希望納期を取り出して受注として登録する | 必須 |
| REQ-002 | 取り出した項目を、必須・型・値の範囲の規則で検証する。規則に合わないものは登録せず、理由を記録する | 必須 |
| REQ-003 | 同じメールが複数回届いても、受注を二重に登録しない | 必須 |
| REQ-004 | 登録済みの受注を、受注月・顧客で絞り込んで一覧できる | 必須 |
| REQ-005 | 受注月ごとに、顧客別・商品別・顧客×商品別の件数と数量合計を集計できる | 必須 |
| REQ-006 | 月次集計を CSV と Excel で出力する。毎月の定期実行ができる | 必須 |
| REQ-007 | 月次集計の CSV から、体裁の整った月次受注帳票（Excel）を作成できる | 必須 |
| REQ-008 | 生成 AI（LLM）が使えないときも、規則による抽出で取り込みを続けられる | 必須 |

## 4. 非機能要件

| ID | 区分 | 要件 |
|---|---|---|
| REQ-009 | 重複防止 | 同じメール（Message-ID が同じもの）の登録は、同時に届いた場合も 1 件だけになる。データベースの一意制約で保証する |
| REQ-010 | 可用性 | LLM の停止・タイムアウト、API の一時的な失敗があっても取り込みが止まらない。再送しても二重登録にならない |
| REQ-011 | セキュリティ | API キー等の秘匿値をリポジトリに置かない。メール本文はデータベースに保存せず、受注に必要な項目だけを保持する。n8n の実行履歴は成功時に保存せず、失敗時の履歴の保存期間は n8n 側で設定する。外部入力の文字列は、出力する CSV・Excel で数式として動かないようにする |
| REQ-012 | 保守性 | 抽出・検証・登録・集計の各処理を自動テストで確認できる。LLM・外部サービスがなくてもテストが通る |
| REQ-013 | 移行性 | データベースは SQLite で開始し、利用規模が大きくなった場合に SQL Server へ移行できる設計にする |

## 5. 対象外

- 受注後の在庫引当・出荷指示・請求処理
- 添付ファイル（PDF・Excel の注文書）の読み取り
- 顧客名・商品名の名寄せ（表記揺れの統合）。初回出現時にマスタへ仮登録し、統合は運用で行う
- 利用者の認証・画面（API は社内ネットワーク内での利用を前提とする。公開する場合の対策は 02_方式設計.md に記載）
